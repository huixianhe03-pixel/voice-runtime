# AGENTS.md

## 四条底线

题面写明：加分项不能替代这四条。违反任何一条不是瑕疵，是不及格。

1. 旧 generation 的音频不得重播
2. 播放状态基于**实际消费**而非生成完成
3. 取消覆盖整个 session 生命周期
4. 关键时序问题必须能被测试复现

每次觉得某处"差不多了"，回来对一遍。

- 不接真实 VAD / ASR / TTS。题面明说不加分，而且会吃掉核心部分的时间。

## 不变量

这些全是**不会报错**的破坏方式——代码看起来合理、能跑、测试可能也过。
靠 review 抓不住，所以写成规则。

| 不变量 | 常见破坏方式 |
| --- | --- |
| 所有队列有容量上限，一个都不能漏 | 顺手写了 `asyncio.Queue()` 不带 maxsize |
| 音频入口永不阻塞 | 给 frame_bus 用了阻塞队列，麦克风被反压 |
| 音频通路永不丢帧 | 给播放队列用了丢弃策略，语音中间出现断裂 |
| `played_samples` 只有 sink 能写 | 某个组件"顺便"更新一下播放进度 |
| 没有裸 `create_task` | 起个后台任务图省事，孤儿任务就出现了 |
| `fence++` 排在 `cancel()` 之前 | 顺序写反，中间窗口的 in-flight chunk 合法通过检查 |
| 每个异步任务按值捕获自己的 generation id | 任务体内读全局 `current_gen`，取消后读到新值 |
| 超时跑在注入的 clock 上 | 用了 `asyncio.wait_for`，虚拟时钟下立刻超时或永不超时 |
| 下一轮上下文只放"听到的" | 结算时把 `generated_text` 整段塞进去 |

要破坏其中一条，先说为什么。

## 工作流

1. **先定架构再写代码。** 组件拆分、状态机、generation 隔离机制、账本数据模型、
   两阶段打断流程定下来之前不写实现。
2. **按依赖顺序实现**：时钟 → 任务 scope → 队列/事件/音频 → 账本 → player →
   endpointer/bargein → 编排器 → 场景 → 测试。
3. **每个场景端到端跑通之后，把 trace 打出来，人读一遍。**
   这一条不能省，理由见修订记录第 2 条。
4. **每写完一个并发原语，写一个一次性探针脚本去捅它**，不要只依赖测试通过。
   探针针对的是：取消之后的残留、同一 tick 内的状态翻转、
   异常路径下另一个任务是否还阻塞着。探针可以写完就删，
   但发现的问题必须留一个回归测试。理由见修订记录第 3 条。
5. 发现 bug 时先说症状和根因，再改。

## 测试的标准

题面原话：验证**行为**而非"没报错"。

- 每个断言都要能想清楚"什么样的错误实现会让它失败"。想不出来就删掉重写。
  例：场景 A 的"无额外排队"拿实测值和 provider 固有延迟之和比——
  改成分段等待就会失败。
- 时序断言（如 250ms）必须跑在虚拟时钟上。真实时钟下 CI 负载一高就 flaky。
- 反向断言优先：`stale_chunk_played_count == 0`、`close 后活跃任务数 == 0`、
  `每个 resumed 前面都有 paused`。
- 断言失败时，先判断是**实现错了**还是**断言写错了**，把判断过程说出来。
  这两种都遇到过，答案不同（修订记录第 4 条）。

## 文档的标准

- 不要每节都配表格。表格只在真的是并列关系时用，论证过程用散文。
- 加粗要稀疏。一节里超过两三处加粗就是在喊。
- 不用 ★、✅ 这类符号，不用 emoji。
- 不用"核心命题""此设计的核心价值"这类推销式措辞。陈述就行。
- 第一人称，承认不确定。数字是拍的就写"这个数是我拍的"。
- 结构要不均匀。每节长度差不多是生成的特征。
- **写进文档的每个数字都必须有来历**：实测的标出来自哪个场景，
  拍的就说是拍的，不写既不实测也不说明的数。
- 局限和开放问题单独成节，写具体的。

反面例子：
> **核心洞察：** Player 是唯一跨格的组件。这一设计决策带来了**三个关键优势**：✅ …

正面例子：
> Player 是唯一跨格的组件：它在数据方向上属于 Egress，但寿命和 Ingress 一样长。
> 三个原因：它持有 fence……

## 范围控制

评分表里代码结构只占 10%，状态模型 + 并发取消占 50%。所以：

- 不在 Fake Provider 上镀金。它只需要可配置 + 确定性。
- 不写抽象层、插件机制、配置文件加载器。
- 加分项只做两个：**可注入虚拟时钟**（同时让测试不 flaky，是刚需）、
  **从日志自动生成时序图**（几十行，而且是"只看日志能解释"最强的证明）。
  其余一个不做。
- 发现自己在写第三层抽象就停下来问。

README 里如实写"已完成"和"未完成"。未完成那一栏写具体、按重要性排序，
是加分不是减分。

## 修订记录

下面每一条都是先出了事、才加进这份文件的。

**1. 「岔路清单」是事后补的，而且补的时候发现它没被执行好。**
最初只有「不替我做决定」一句原则，没有清单。结果技术栈、阈值取值、
play_q 容量、`turn_id` 语义四个决定实际是 agent 拍的，我事后才注意到。
补清单的时候我把"谁定的"这一列如实标了出来，而不是改成好看的版本——
这四个里 `turn_id` 那个还导致 DESIGN.md 和代码短暂不一致（文档说"turn 不变"，
代码是 turn++），后来对着代码改了文档。

**2. 「人读一遍 trace」从建议升格为必须。**
场景 C 第一次跑通时测试全绿，但我把 trace 打出来看才发现 **turn 2 根本不存在**——
`Endpointer.arm()` 把 `_saw_speech` 重置为 False，而确认打断时用户正在说话，
那段语音就是新一轮的开头，于是后续的 `speech_end` 不触发任何评估，机器人从此沉默。
测试没抓到，因为我当时还没写针对 turn 2 的断言。**测试只验证你想到的东西。**

**3. 「写探针去捅它」是加的。**
写完之后测试 64 个全绿，我又拿一次性脚本去捅并发路径，捅出两个：
LLM 抛异常时 TTS 永远阻塞在 `inq.get()`（`asyncio.wait` 默认 `ALL_COMPLETED` 不返回，
最后是看门狗兜住的，终态被记成 `timed_out` 而不是 `failed`，归因错了）；
以及 pause 和 resume 落在同一帧内时 sink 观察不到暂停标志，
日志里出现一个孤立的 `playback_resumed`。
第二个功能上完全正确，坏的是**日志自洽性**——而"只看日志就能解释这一次执行"
是这道题的评分标准。两个都有回归测试在 `tests/test_trace_integrity.py`。

**4. 「断言失败时先判断是实现错还是断言错」是加的。**
第一次全量跑测试 12 个失败，其中 10 个是我把 `generation_id` 当成 payload 字段读了
（它是 Event 的顶层字段），2 个是断言本身选错了角度：
场景 B 我断言停顿期静音时长 ≥600ms，实测 580ms——因为 VAD 有 60ms hangover
且评估日志每 100ms 才记一次。改成断言"超过了 complete 档的 400ms 却仍然 wait"
才是真正的证据。`play_q` 那条也一样：整段回复只有 4 个 chunk，
容量 5 和 100 都装得下，队列从没满过，得把小缓冲压到 1 个 chunk 才测得出来。

**5. 「不代笔经历」是加的。**
DESIGN.md 第一版里有一句"我第一版让任务读 `self.current_gen`，结果打断之后
旧 TTS 读到了新 gen id"——那件事没发生过，是 agent 替我写的。
技术上完全真实（按引用捕获的经典 bug），但不是我的经历。删掉了，
改成陈述这个模式为什么危险。后来实战找到的三个真 bug 比编的那个有说服力得多。

**6. 「文档的标准」整节是加的。**
DESIGN.md 第一版每节都配表格、表格都对称填满、加粗撒得到处都是、
还用了 ★ 符号。我判断它一眼就能看出是生成的，要求全文重写。
现在这一节写的就是重写时定下的规则。
